# AUDIT_PRINCIPLES — EarthMesh v3 网格审查总原则

> 适用范围：本文件仅针对 **EarthMesh v3 当前项目本身**（Rust-native + GUI + GIS workflow）。
> 审查时把 v3 当作一个独立项目，不引用、不比较、不依赖任何旧版本实现。
> 本文件是 [PROJECT_AUDIT_PLAN.md](./PROJECT_AUDIT_PLAN.md)、[REPORT_TEMPLATE.md](./REPORT_TEMPLATE.md)、
> [TASK_STATUS.md](./TASK_STATUS.md) 的判定基准；任何结论、bug 判定、refinement 评价都必须回溯到本文件的原则。

---

## 1. 总原则（Refinement 的黄金法则）

**不要为了"细化更多"而细化。**

任何 refinement（网格细化）都必须**同时满足**以下五个条件，缺一不可：

1. **该区域存在重要空间异质性**；
2. **这种异质性会影响目标模式的关键物理过程**；
3. **细化带来的物理收益大于计算成本**；
4. **细化后网格仍满足几何质量、拓扑质量、数值稳定性和耦合一致性要求**；
5. **GUI 能让用户理解为什么这里需要细化，以及细化后质量是否变好。**

> 审查判据：对任何一个 refinement 触发条件 / 阈值 / 工作流，逐条核对上述五点。
> 若某条无法被代码、配置或文档证明成立，则该 refinement 行为视为**可疑**，须进入 Bug Table 或 Physical Consistency Table。

---

## 2. EarthMesh v3 的目标

EarthMesh v3 应该成为一个**更通用、更可靠、更高网格质量、更符合物理过程需求**的地球系统非结构网格制作平台。

它不应只是"根据几个阈值细化网格"的工具，而应能根据以下因素**共同**生成更合理的
land / ocean / atmosphere / land-ocean coupled mesh：

- 目标模式需求（CoLM2024 / FVCOM / MPAS / OLAM / IAP 等）；
- 物理过程敏感性；
- 输入数据空间异质性；
- 水文 / 海岸 / 陆海耦合特征；
- 网格质量约束；
- 计算成本预算；
- GUI workflow。

## 3. 原则的可操作化（审查时如何落地）

每条总原则在审查中对应一组**可检验的问题**。审查员在填写各报告表格时，必须能对每条给出证据（代码位置 / 测试 / 配置 / 数据）。

### 3.1 空间异质性（原则 1）
- 异质性度量来自哪个输入字段？（地形 / land type / LAI / 土壤 / 岸线 / 河网 …）
- 度量是 mean/std/梯度/分位数中的哪一种？阈值定义在何处、单位是否一致？
- 异质性的空间分辨率与目标网格分辨率是否匹配（避免欠采样 / 过采样）？

### 3.2 物理过程相关性（原则 2）
- 该字段对应目标模式的哪个物理过程（地表能量 / 水文汇流 / 海岸动力 / 陆海通量）？
- 细化是否真的改善该过程的可解析性，还是仅仅改变了网格密度？

### 3.3 收益 vs 成本（原则 3）
- 细化前后单元数 / 边数 / 最小边长（时间步约束）如何变化？
- 是否存在成本预算（cell 数上限、CFL/最小边长约束）来约束细化？

### 3.4 网格质量与一致性（原则 4）
- **几何质量**：单元面积、长宽比、最小角、well-centered 性、对偶六边形质量。
- **拓扑质量**：闭合性（closed mesh）、邻接一致性（Method-C neighbors）、无悬挂边 / 重复点。
- **数值稳定性**：最小边长 / 梯度比（refinement ratio）是否受限、是否平滑过渡。
- **耦合一致性**：land/ocean/atmos 之间、以及与 hydro/coast 掩膜之间的边界、掩膜、索引是否一致。

### 3.5 GUI 可解释性（原则 5）
- GUI 是否展示"为什么这里被细化"（触发字段、阈值、命中区域）？
- GUI 是否展示"细化后质量是否变好"（质量指标对比、before/after）？
- 用户能否在 GUI 中追溯一次 run 的完整 workflow 与参数？

---

## 4. 审查的非目标（防止越界）

- 不追求"细化越多越好"，也不追求"网格越大越省"——以**总原则的五条**为唯一裁判。
- 不引入对旧版本的对比作为正确性依据；正确性只能由 v3 自身的物理定义、几何/拓扑约束、测试与文档支撑。
- 不在 read-only 阶段修改任何 `src/rust` 代码（见 [PROJECT_AUDIT_PLAN.md](./PROJECT_AUDIT_PLAN.md) 的阶段权限）。

## 5. 证据等级（结论可信度分级）

填写报告时，每条结论标注证据等级：

| 等级 | 含义 | 触发动作 |
|------|------|----------|
| **A — 已证实** | 有代码位置 + 测试/复现可佐证 | 直接进入对应报告表 |
| **B — 强推断** | 有代码位置，但无测试直接覆盖 | 进入报告表，并在 Patch Plan 提议补测试 |
| **C — 疑似** | 仅静态阅读，存在多种解释 | 进入 Open Questions，需进一步验证后才升级 |
| **D — 假设** | 尚无代码证据 | 仅记录在 TASK_STATUS 的 Open questions |

> 任何 A/B 级"正确性 bug"必须给出文件:行号；C/D 级不得直接写入 Bug Table。
